# ADR-003: Матрица поддерживаемых браузеров, потоковая безопасность и бюджет памяти

- **Статус:** Принято (Accepted)
- **Дата:** 2026-10-26
- **Контекст:** Этап 0 технического спайка SonoForge Web (Спецификация §6, §7, Этап 0)

---

## 1. Поддерживаемая матрица браузеров и устройств

| Класс окружения | Поддерживаемые версии | Уровень поддержки в v1 |
|---|---|---|
| Desktop Chromium (`Chrome`, `Edge`) | Последние 2 стабильные мажорные версии (Windows / macOS / Linux) | **Tier 1 (Полная поддержка, включая выбор папок и OPFS)** |
| Desktop `Firefox` | Последние 2 стабильные версии + актуальный Firefox ESR | **Tier 1 (Полная поддержка)** |
| Desktop `Safari` (macOS) | Последние 2 мажорные версии (Safari 17+) | **Tier 1 (Полная поддержка)** |
| Планшеты (`iPadOS Safari`, `Android Chrome`) | Актуальные стабильные версии, экран `>= 1024 px` в альбомной ориентации | **Tier 2 (Просмотр, cine, базовые линейные измерения pointer-событиями)** |
| Устаревшие браузеры без WebAssembly / ES2022 Module Workers / узкие экраны смартфонов (`< 768 px`) | Не поддерживаются для диагностической разметки | Явное предупреждение о неподдерживаемом окружении |

### Обязательные браузерные API (доступны во всех браузерах Tier 1 и Tier 2 без `SharedArrayBuffer`)
- `WebAssembly` (однопоточные WASM-кодеки без обязательного `COOP/COEP` заголовка `SharedArrayBuffer`, что упрощает встраивание в клинические порталы и PACS).
- `Worker` (`type: 'module'`) + `Transferable` `ArrayBuffer`.
- `IndexedDB` + `StorageManager.getDirectory()` (OPFS — при наличии, с прозрачным fallback на IndexedDB Blob store).
- `CanvasRenderingContext2D` с учётом `window.devicePixelRatio` и `Pointer Events`.

## 2. Изоляция памяти и потоков при работе с многокадровым ЭхоКГ

Эмпирический замер на Этапе 0 (`docs/spike/results/dicom_engine_bench.json`) показал:
- Один цветной (`RGB`) кадр `1280×720` занимает **2.64 MiB** сырых пикселей, а клип из 120 кадров — **316.41 MiB** (при 5–8 открытых петлях в серии вкладка без лимитов превышает 2 GiB и аварийно завершается браузером).
- Реализованный `LruFrameCache(96 MiB)` удерживает пиковое потребление декодированных кадров одного воркера строго в пределах **94.93 MiB** (36 резидентных кадров, детерминированное вытеснение LRU без утечек).

### Принятые инварианты архитектуры рендеринга и памяти
1. **Ленивый старт воркера:** оболочка приложения (`88.7 KiB` gzip) монтируется до создания DICOM Web Worker и загрузки WASM-кодеков.
2. **Разделение буфера измерений и буфера отображения:**
   - в `LruFrameCache` воркера хранится `DecodedMeasurementFrame` (`Uint8Array | Uint16Array | Int16Array`) без применения `Window/Level`;
   - для отрисовки на `<canvas>` воркер формирует отдельный `RGBA` `ArrayBuffer` и передаёт его в главный поток через `postMessage(..., [rgbaBuffer])` (`zero-copy transfer`), исключая удвоение буферов при пересылке.
3. **Кооперативная отмена задач (`cancelTask`):** при быстром переключении серий или скраббинге устаревшие запросы декодирования отменяются по `requestId` без блокировки очереди воркера.

## 3. Политика информационной безопасности и защиты PHI

1. **Рекомендуемый базовый HTTP Content-Security-Policy для production-сборки:**
   ```http
   Content-Security-Policy:
     default-src 'self';
     script-src 'self' 'wasm-unsafe-eval';
     worker-src 'self' blob:;
     style-src 'self';
     img-src 'self' data: blob:;
     connect-src 'self';
     object-src 'none';
     base-uri 'self';
   ```
   При подключении опционального профиля `DICOMweb` (Этап 6) в `connect-src` явно добавляется только настроенный origin DICOMweb-шлюза.
2. **Запрет утечки PHI:**
   - режим `Hide PHI` включён **по умолчанию** (`[REDACTED]` для `PatientName`, `PatientID`, `PatientBirthDate`, `InstitutionName`);
   - запрещено помещать ФИО, `PatientID`, дату рождения и сырые `StudyInstanceUID`/`SOPInstanceUID` в URL, `localStorage`, заголовки аналитики и `console.*`;
   - локальный контур импорта и расчётов гарантирует **0 исходящих сетевых запросов** с данными исследования.
