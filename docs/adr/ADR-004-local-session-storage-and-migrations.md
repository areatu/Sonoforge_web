# ADR-004: Локальное хранение рабочих сессий, версионирование схемы и синхронизация вкладок

- **Статус:** Принято (Accepted)
- **Дата:** 2026-10-26
- **Контекст:** Этап 0 технического спайка SonoForge Web (Спецификация §4, §6, §7, Этап 0)

---

## 1. Контекст и проблема

В local-first браузерном приложении врач или исследователь выполняет трудоёмкую ручную разметку (линейные калиперы, калибровка по линейке, контуры Симпсона на ED/ES кадрах, допплеровские трассы, ввод антропометрии). Случайное обновление вкладки (`F5`), закрытие браузера или открытие второй вкладки не должно приводить к потере или тихому затиранию измерений. При этом браузерные хранилища имеют квоты, могут очищаться ОС при нехватке диска и на общих рабочих станциях требуют быстрой очистки локальных данных.

---

## 2. Решение: Двухуровневое локальное хранилище (`IndexedDB` + опциональный `OPFS`)

### 2.1. Разделение метаданных сессии и тяжёлых бинарных DICOM-данных

1. **`IndexedDB` (`sonoforge_web_db`) — структурированные данные рабочих сессий (обязательный слой):**
   - `sessions`: паспорт рабочей сессии (`sessionId`, `schemaVersion`, монотонная `revision`, `updatedAt`, `studyFingerprint`, обезличенный контекст роста/веса/ЧСС/ручного BSA, флаг `phiPersisted: false`).
   - `measurements`: нормализованные записи линейных измерений, площадей, контуров Симпсона, допплеровских огибающих и пользовательских калибровок `manual_ruler` в координатах исходного кадра `(col, row)` с привязкой к `(sopInstanceUidHash, frameIndex)`.
   - `audit_migrations`: журнал применённых миграций схемы.
2. **`OPFS` (Origin Private File System) / `IndexedDB Blobs` — временный кеш локальных DICOM-файлов (опциональный слой с квотой):**
   - По умолчанию при локальном открытии файла DICOM-байты удерживаются только в памяти воркера на время активной вкладки (режим **Ephemeral PHI-Safe** для общих клинических терминалов).
   - Пользователь может явно включить переключатель **«Кешировать DICOM локально для восстановления после перезагрузки»**: тогда сырые `.dcm` сохраняются в `OPFS` (или `IndexedDB` fallback в средах без OPFS) с проверкой `navigator.storage.estimate()` и кнопкой **«Очистить все локальные данные»** в 1 клик.
   - Если после перезагрузки страницы сессия измерений найдена в `IndexedDB`, а DICOM-байты не были закешированы, пользователь может повторно выбрать ту же папку/файлы — измерения автоматически перепривязываются по хешу `SOPInstanceUID` и размерам кадра.

## 3. Схема сессии, миграции и защита от конфликтов между вкладками

### 3.1. Версионированный контракт JSON / IndexedDB (`schemaVersion` + `revision`)

Прототип Этапа 0 уже реализует сериализацию `ExportedSessionV1`:
```json
{
  "schemaVersion": 1,
  "revision": 4,
  "exportedAt": "2026-10-26T12:00:00.000Z",
  "patientContext": {
    "heightCm": 176,
    "weightKg": 78,
    "manualBsaM2": null,
    "lvotVtiCm": 21.5,
    "avVtiCm": 52.0,
    "avVmaxCmPerSec": 265,
    "heartRateBpm": 68
  },
  "manualCalibrationsMmPerPx": {},
  "linearMeasurements": [],
  "simpsonContours": {}
}
```
- Каждое изменение состояния схемы сопровождается чистой детерминированной функцией миграции `migrateSession(vN -> vN+1)` с unit-тестами на фикстурах всех предыдущих версий.
- Экспорт сессии в JSON по умолчанию **не включает PHI** (`PatientName`, `PatientID`, `PatientBirthDate`, `InstitutionName`).

### 3.2. Защита от тихой перезаписи между двумя вкладками (`Optimistic Concurrency + BroadcastChannel`)
1. Каждая запись в `IndexedDB` выполняется транзакцией с проверкой `stored.revision === expectedRevision`. Если условие нарушено (другая вкладка уже сохранила `revision + 1`), запись отклоняется с явным событием `SessionRevisionConflict`.
2. Канал `BroadcastChannel('sonoforge-session-sync')` мгновенно уведомляет соседние вкладки того же origin об обновлении `sessionId` и `revision`, предлагая пользователю перезагрузить актуальную ревизию или сохранить копию (fork) текущей вкладки.
