# SonoForge Web — план-спецификация переноса в браузер

**Статус:** проект предложения к реализации  
**Дата:** 2026-10-26  
**Исходный проект:** [SonoForge](https://github.com/areatu/SonoForge) (Python / PySide6, GPL-3.0)  
**Целевой проект:** отдельное браузерное приложение **SonoForge Web** в отдельном GitHub-репозитории  
**Основной язык веб-клиента:** TypeScript  

> Этот документ фиксирует рекомендуемые границы и порядок работ. Он не является медицинской валидацией или разрешением использовать приложение для клинической диагностики. До начала полноценной разработки необходимо выполнить технический спайк и зафиксировать выбор DICOM-движка и способа повторного использования/переноса расчётного ядра.

## 1. Резюме и цель

Создать самостоятельное веб-приложение SonoForge для открытия и анализа эхокардиографических DICOM-исследований в современном браузере. Исходное Qt-приложение продолжает развиваться отдельно; веб-клиент не должен зависеть от его интерфейса или собираться из PySide6.

Целевой принцип: **локальная обработка исследования в браузере, ручной ввод измерений, прежние формулы SonoForge, никаких обязательных загрузок данных пациента в облако**.

### Целевой пользовательский сценарий

1. Пользователь открывает сайт SonoForge Web.
2. Загружает DICOM-файл(ы) или папку исследования либо подключается к настроенному DICOMweb-серверу.
3. Выбирает исследование, серию, кадр/кинопетлю и нужную проекцию.
4. Просматривает изображение, регулирует окно/уровень, масштаб, позицию и воспроизведение.
5. Вручную выполняет измерения и при необходимости рисует freehand-контуры/задаёт анатомические точки.
6. Получает расчёты и отчёт, может сохранить локальную сессию или экспортировать результат.

## 2. Продуктовые границы

### 2.1 Включить в первую основную версию

- Импорт DICOM локально: выбор файлов, drag-and-drop, папка там, где это поддерживает браузер; сборка исследования и серий по DICOM UID.
- DICOM-метаданные: просмотр ключевой информации об исследовании, серии и кадре с возможностью скрыть идентифицирующие поля.
- 2D-просмотр эхокардиографии: одиночный кадр и multi-frame/cine, навигация по кадрам, воспроизведение/пауза, скорость, loop.
- Управление изображением: pan, zoom, fit/reset, window/level, поворот/отражение при поддержке ориентации, текущий кадр и масштаб.
- Ручные инструменты: линейные калиперы, углы/планиметрия по поддержанным рабочим процессам, freehand-контур и заданные пользователем ориентиры.
- Ручная настройка калибровки и поддерживаемая автоматическая калибровка по DICOM-метаданным/линейкам, если её можно перенести без зависимости от Qt.
- Расчёты и калькуляторы SonoForge, перечисленные в разделе 4; сохранение происхождения входных значений и единиц измерения.
- Рабочая сессия с измерениями, привязанными к исследованию/серии/кадру; локальное сохранение и восстановление с проверкой ревизии.
- Отчёт и экспорт поддержанных результатов (как минимум печатная HTML/PDF-форма после проверки браузерного экспорта).
- Русский и английский интерфейс; доступность клавиатурной навигации и понятные ошибки.
- Совместимость с последними стабильными версиями Chrome/Edge и Firefox; Safari — после отдельной проверки файловых API и декодеров.

### 2.2 Включить только после MVP / отдельным решением

- DICOMweb: поиск исследований и получение серий по QIDO-RS/WADO-RS; загрузка результатов в PACS через STOW-RS — после оценки рисков и отдельного подтверждения пользователя.
- Отображение нескольких синхронизированных панелей.
- PACS-профили и аутентификация, расширенные настройки кэширования, PWA/offline shell.
- Расширенный экспорт PDF/XLSX/video и перенос сложных протоколов отчёта.
- Doppler, M-mode, ECG и расширенные калькуляторы — они входят в целевой паритет по бизнес-логике, но могут запускаться поэтапно после базового просмотра.

### 2.3 Не включать в начальный веб-проект

- ONNX / ML-модели, AI-сегментация, авто-контурирование, AI refinement, temporal fusion и автоматическое распространение контуров.
- Speckle tracking / STE и оптический поток.
- DIMSE (C-FIND/C-MOVE/C-GET/C-STORE), встроенный Storage SCP и любой собственный PACS-сервер.
- Необязательная облачная загрузка DICOM, хранение случаев на стороне SonoForge, аккаунты/подписки/публичные share-ссылки.
- Полный паритет Qt-интерфейса, Presenter и редактор справочников.
- Заявления о диагностическом назначении или клинической эквивалентности до отдельной валидации.

**Терминология контуров:** исключаются автоматическое обнаружение и генерация контуров. Ручной freehand-контур и точки-ориентиры остаются как инструменты ввода, если они нужны пользователю для расчёта Simpson и других геометрических калькуляторов. Если требование трактуется как «не иметь вообще никаких контуров», соответствующие расчёты LV volumes/LVEF нельзя считать сохранёнными без другого валидированного способа ввода геометрии.

## 3. Архитектурные принципы

1. **Отдельный репозиторий.** Репозиторий содержит веб-клиент, тесты, документацию, lock-файлы зависимостей и CI; сборка не изменяет настольное приложение.
2. **TypeScript для browser UI и клиентской логики.** Стартовый стек — React + TypeScript + Vite. Выбор UI-библиотеки не должен связывать медицинские расчёты с компонентами React.
3. **Модульные границы:** `viewer` (DICOM/пиксели), `tools` (жесты и оверлеи), `domain` (единицы/формулы/калькуляторы), `application` (сессии и use cases), `storage` (локальная запись), `adapters` (DICOMweb, импорт файлов, экспорт).
4. **Один источник правды для формул.** Предпочтительный конечный вариант для самостоятельного TS-проекта — перенос нужных чистых расчётов в TypeScript с дифференциальными тестами против Python-реализации и существующих golden/reference случаев. Не переписывать формулу «по памяти» и не менять округление/единицы без зафиксированной причины.
5. **ADR перед фиксацией runtime:** сравнить (A) TypeScript-перенос формул, (B) Pyodide для вызова исходного Python-домена из браузера, (C) Python API. Для MVP рекомендуется локальный TS-клиент без обязательного сервера; Pyodide — только если спайк показывает, что его старт, зависимости и память приемлемы. Python API не должен быть единственным способом открыть локальное исследование: иначе потребуется отправлять медицинские изображения на сервер.
6. **DICOM-движок за интерфейсом.** На спайке сравнить Cornerstone3D и DWV на реальных обезличенных эхокардиографических DICOM: multi-frame, transfer syntax, cine, геометрия, скорость. Выбор библиотеки скрыть за интерфейсами `DicomFileReader`, `FrameSource`, `SeriesAssembler`, чтобы иметь возможность заменить декодер.
7. **Никакого скрытого сетевого трафика с изображениями.** В локальном сценарии DICOM-пиксели остаются в браузере. Сетевые запросы к PACS разрешены только после явного включения DICOMweb и показываются пользователю.
8. **UI-слой не содержит медицинских формул.** Компоненты вызывают типизированные use cases; домен не импортирует React, браузерные API или DICOM-библиотеку.

### Предварительная структура веб-репозитория

```text
Sonoforge_web/
├── apps/web/                 # React/TypeScript app
├── packages/domain/          # формулы, модели, единицы, протоколы
├── packages/dicom/           # DICOM parser/decoder adapters
├── packages/viewer/          # viewport, cine, overlays, tools
├── packages/application/     # study/workspace/session use cases
├── packages/storage/         # IndexedDB/OPFS/local export
├── tests/golden/             # JSON-векторы Python ↔ TypeScript
├── docs/                     # архитектура, privacy, help, release
└── .github/workflows/        # lint, unit, e2e, build, security checks
```

Структура уточняется после спайка; не создавать пакетные границы ради границ, если MVP пока небольшой.

## 4. Функциональная матрица переноса

| Область SonoForge | Веб-решение / требование | Ограничение первого релиза |
|---|---|---|
| DICOM import/local studies | File System Access API при наличии + fallback на input files/drag-and-drop; DICOM parser в браузере | Рекурсивная папка и крупные исследования проверяются отдельно для каждого браузера |
| Multi-frame/cine | Web Worker для парсинга/декодирования, `requestAnimationFrame` для воспроизведения, ограниченный буфер кадров | Не загружать весь cine в память без измерения бюджета |
| Lossless correctness | Измерения считаются по исходному/декодированному без потерь кадру и исходной геометрии; preview-путь отделён от измерительного | Никакой lossy-картинки для расчётов без явного валидированного правила |
| Viewer tools | Canvas/WebGL viewport с отдельным слоем оверлеев; pointer events; экранные координаты преобразуются в координаты изображения | Проверить масштабирование HiDPI, touch, сохранение геометрии при zoom/pan |
| Линейные измерения | TS-перенос геометрии, единиц, маркировки и workflow; сохранять данные и точность | Устройство/калибровка должны быть известны; иначе показывать пиксели, не мм |
| Freehand и Simpson | Ручной trace/landmarks; пересчёт в координаты изображения; существующие алгоритмы Simpson и freshness/provenance | Никакого автоматического рисования/уточнения контуров |
| Допплер | Калибровка осей, baseline, пики/циклы, VTI, индексы PSV/EDV/RI/S-D и связанные калькуляторы | Этап после просмотра и базовых measurement workflows; отдельные golden-тесты |
| M-mode / ECG | Перенос калибровок/экстракции/HR и вычислений; графики на Canvas/WebGL или лёгком chart layer | Графические интеракции и производительность проверяются отдельно |
| ASE/калькуляторы | Реестр калькуляторов, формулы, нормы/градации, единицы, форматирование и provenance из домена | Браузер не должен подменять отсутствующее значение нулём или молча менять единицы |
| Персистенция | Версионируемая JSON-сессия в IndexedDB/OPFS и export/import; запись по study UID с локальной ревизией | Локальное хранилище не является долговременным архивом; пользователь управляет резервной копией |
| DICOMweb/PACS | QIDO/WADO/STOW-адаптер через Fetch; настройка endpoint, auth, cancellation, прогресс | CORS/HTTPS — ответственность PACS или reverse proxy; не обходить browser security |
| PDF/отчёты | HTML print-to-PDF для первого этапа; позже проверить PDF/XLSX generation | Экспорт должен явно указывать использованные измерения и единицы |

Расчётный каталог должен сверяться с `src/echo_personal_tool/domain/calculations/`, `domain/calculators/` и соответствующими workflow текущего клиента. Матрица функций и список формул должны быть опубликованы как versioned checklist в веб-репозитории до объявления паритета.

## 5. Модель данных и поведение

### 5.1 Сущности

- `StudyRef`: UID, отображаемые метаданные, локальный/удалённый источник.
- `SeriesRef`: Series UID, modality, описание, dimensions, frame count, transfer syntax.
- `ImageFrameRef`: SOP Instance UID, номер кадра, геометрия, pixel spacing, timestamp/temporal index при наличии.
- `Measurement`: тип, значения и единицы, точки/геометрия в координатах изображения, привязка к frame/series/study, дата создания, источник ввода и версия алгоритма.
- `CalculationResult`: тип расчёта, входы, выходы, единицы, warnings, freshness/revision и происхождение каждого входа.
- `WorkspaceSession`: выбранное исследование, состояние viewport, measurement collection, calibration, language/preferences.

Не записывать PHI в URL, телеметрию, console log, сообщения об ошибках или продуктовую аналитику. UID также считать чувствительными метаданными.

### 5.2 Автосохранение

- Локальное автосохранение — только после уведомления/понятного статуса и с возможностью отключить/очистить.
- Импорт/экспорт сессии включает schema version и миграцию формата.
- При конфликте двух вкладок сохранять ревизии и показывать конфликт; не перетирать более новую сессию молча.
- При недостатке квоты IndexedDB/OPFS показать понятную ошибку, предложить экспорт и не удалять пользовательские результаты автоматически.

## 6. Нефункциональные требования и критерии приёмки

Численные показатели ниже являются **начальными бюджетами**, которые надо подтвердить на спайке на типовых устройствах; они не заменяют тесты на разных браузерах.

### Производительность

- Первичная оболочка приложения без DICOM-файлов отображается до загрузки DICOM runtime/worker.
- Нет обязательной загрузки AI-моделей или ONNX runtime; холодный запуск не скачивает model weights.
- Загрузка DICOM не блокирует интерфейс: parsing/decode и большие операции идут в Web Worker, UI показывает прогресс и возможность отмены.
- Для типового 2D кадра 720p целевой отклик на навигацию — до 150 мс после кадра в памяти; воспроизведение cine стремится к 25–30 fps на референсном ПК. Если эти значения недостижимы на выбранном codec path, фиксируется graceful fallback (понижение preview quality, предзагрузка, серверный rendered frame) без влияния на точность измерений.
- Ограничить кэш декодированных кадров конфигурируемым бюджетом; измерить пиковую память на тестовом cine и исследовании из нескольких серий.
- Размер initial JS/CSS и время до интерактивности измерять в CI; большие DICOM/графические библиотеки загружать по необходимости.

### Точность и соответствие

- Каждый перенесённый расчёт имеет unit tests и набор входов/выходов, полученный от проверенной Python-реализации (golden vectors).
- Для численных сравнений заранее определить допуск по каждому типу результата; не использовать один произвольный epsilon для всех единиц.
- Проверять пустые, нулевые, невалидные, устаревшие, частично заданные и конфликтующие входы.
- Геометрия измерения остаётся привязанной к исходному кадру при pan/zoom/resize и восстановлении сессии.
- Нет использования lossy preview-пикселей как базы для измерения.
- Для каждой функции в матрице явно отмечено: `implemented`, `validated`, `deferred` или `not supported`.

### Безопасность и приватность

- По умолчанию локальные DICOM-файлы не отправляются в сеть.
- DICOMweb credentials не хранить в localStorage в открытом виде; предпочтительно ввод на сессию и отказ от запоминания; persistent secret storage требует отдельного threat model.
- CSP, защита от XSS, запрет небезопасного HTML из DICOM metadata, dependency scanning и HTTPS для развёртывания.
- Все сетевые endpoints показывать и проверять; предупреждать об отправке изображений при STOW.
- Чёткое предупреждение об образовательном/исследовательском назначении и необходимости независимой клинической проверки.
- Для тестовых материалов использовать только синтетические или деидентифицированные исследования. Golden fixtures должны быть проверены на отсутствие PHI.

### Надёжность и доступность

- Ошибки unsupported transfer syntax, повреждённого файла, нехватки памяти и отсутствующего CORS разбираются по-человечески, с сохранением незатронутой сессии.
- Горячие клавиши не перехватывают ввод в текстовых полях; базовые функции доступны мышью и клавиатурой.
- Интерфейс не полагается только на цвет; масштабируется до узкого экрана, хотя основная оптимизация — десктопный viewport.

## 7. План этапов и gate-критерии

### Этап 0 — Спайк и архитектурные решения

Спайк проводится **в отдельном репозитории SonoForge-Web**, а не в основном SonoForge. Репозиторий можно создать до подтверждения архитектуры; на этом этапе в нём находятся только прототипы и тестовые скрипты, без обещания стабильного продукта и без production-кода. Прототипы после прохождения gate можно переработать или удалить.

**Задачи:**
- Создать репозиторий и минимальную ветку/папку для spike-кода; не менять desktop-ветку и не подключать web-зависимости к desktop-сборке.
- Подготовить небольшой набор обезличенных эхо DICOM: uncompressed, JPEG, JPEG-LS/JPEG2000 (если есть), multi-frame, несколько производителей.
- Прототипировать импорт, чтение metadata, отображение одного кадра и cine в кандидате DICOM-библиотеки.
- Сравнить Cornerstone3D и DWV по поддержке ultrasound multi-frame, transfer syntax, памяти, worker strategy, лицензиям и размеру бандла.
- Реализовать пробный перенос 3–5 ключевых формул в TS и differential test против Python.
- Проверить Pyodide alternative на cold start, пакетном составе и возможности вызова выбранных доменных модулей.
- Зафиксировать ADR: DICOM engine, расчётный runtime, browser support, хранение сессии, лицензионный подход.

**Gate:** есть рабочий браузерный прототип, декодирующий репрезентативные реальные test fixtures; измерены cold start, frame decode, memory; выбран runtime; выявленные несовместимые синтаксисы имеют явную стратегию/fallback. Если ключевые кодеки не удаётся декодировать локально — решить до разработки большого UI, поддерживать ли их через DICOMweb rendered frames.

**Ориентир из feasibility-анализа:** 2–3 человеко-недели на исследовательский спайк; это оценка, не обязательная дата.

### Этап 1 — Каркас production-веб-приложения и CI

Начинается после успешного gate этапа 0. Использовать отдельный репозиторий, созданный для spike; отделить/удалить прототипы и зафиксировать выбранную архитектуру.

- Оформить лицензию и notices, README, локальный запуск и production build.
- Настроить TypeScript strict mode, форматирование/lint, unit tests, Playwright e2e, build artifact и dependency audit.
- Задать границы packages и DICOM/domain/application ports.
- Реализовать shell, локализацию RU/EN, error boundary, consent/privacy notice.

**Gate:** чистый clone запускается по README; CI блокирует merge на ошибке lint/test/build; в production bundle нет секретов и тестовых DICOM.

### Этап 2 — Локальный DICOM ingest и базовый viewport

- Импорт одиночного файла/набора файлов; группировка studies/series; отображение списка и метаданных.
- Worker parsing/decode, transfer syntax reporting, cancellation, прогресс, memory budget.
- 2D viewport, cine navigation, window/level, pan/zoom, reset, ориентационные/кадровые подписи.
- Скрытие PHI overlay по умолчанию, preview metadata без утечки в URL/log.

**Gate:** поддержанные тестовые данные импортируются и корректно организуются; неизвестный codec даёт ясную ошибку; просмотр multi-frame подтверждён e2e.

### Этап 3 — Ручные инструменты, координаты и калибровка

- Система преобразования display↔image coordinates и тесты pan/zoom/HiDPI.
- Калипер, свободный trace, точки-ориентиры, редактирование/удаление/undo, выбор фрейма.
- Ручная и поддержанная автоматическая калибровка; units/provenance.
- Overlay measurements; сохранять геометрию в координатах исходного изображения.

**Gate:** golden UI tests подтверждают, что координаты и расстояния не меняются при преобразованиях viewport; незакалиброванное измерение не выдаётся в миллиметрах.

### Этап 4 — Перенос domain и калькуляторов

- Опубликовать полный каталог необходимых calculators/workflows.
- Перенести расчётные модули TS по одному; подготовить Python-generated JSON vectors с нормальными, граничными и невалидными случаями.
- Добавить BSA/indexation, linear measurements, Simpson (с ручной геометрией), Doppler indices, RV/LA/LV calculations, diastology и прочие включённые калькуляторы по каталогам domain.
- Перенести freshness, value origin, units, warnings и округления; связать UI через application use cases, а не дублировать логику.

**Gate:** 100% формул, объявленных для релиза, проходят согласованные golden tests; в отчёте видны отсутствующие/устаревшие входы и единицы.

### Этап 5 — Study session, локальная персистенция и отчёт

- Сохранение/восстановление session JSON с schema version, revision, metadata minimization.
- IndexedDB/OPFS адаптер, экспорт/импорт сессии, очистка локальных данных.
- Report preview и PDF через print workflow; позже XLSX, если нужен и проверен.
- Проверить несколько вкладок, quota exceeded, crash/reload, conflict handling.

**Gate:** сессия после перезагрузки воспроизводит measurement state и не теряет исходные координаты; экспорт не добавляет невалидированные расчёты.

### Этап 6 — Doppler/M-mode/ECG и расширенные workflows

- Перенос калькуляций и интерактивности по модулям.
- Графики и пики на Canvas/WebGL/chart adapter; отдельные worker/performance tests.
- Vendor calibration и ECG cycle detection только после differential validation.

**Gate:** каждый включённый workflow проходит fixture-based acceptance и performance budget; сомнительное автоопределение можно отключить и выполнить вручную.

### Этап 7 — DICOMweb/PACS (опциональная функция)

- QIDO/WADO, профили подключения, отмена, retry, пагинация и прогресс.
- CORS/reverse-proxy setup guide; авторизация на origin пользователя; не пересылать пароли стороннему backend.
- STOW отключён по умолчанию; перед отправкой — подтверждение destination, состава данных и de-identification state.
- Threat model, audit событий и проверка TLS/certificate behavior.

**Gate:** интеграционные тесты с Orthanc/DICOMweb sandbox, CORS отказ корректно объясняется, локальный сценарий продолжает работать без PACS.

### Этап 8 — Регрессия, accessibility, нагрузка и релиз

- E2E на поддерживаемых браузерах/OS; деидентифицированные golden DICOM; keyboard, HiDPI, resize.
- Performance baseline и бюджет размера бандла; memory/leak tests на длинной cine-сессии.
- SBOM/dependency/license review, CSP/security headers, privacy review.
- Документация установки/self-host, список проверенных transfer syntaxes, ограничения браузеров, known issues.
- Версионирование схемы сессии и API/adapter; релизная заметка с явной feature matrix.

**Gate:** все P0/P1 acceptance criteria закрыты, нет неразобранных ошибок клинической геометрии/чисел, docs соответствуют фактическим возможностям. Релиз маркируется как non-diagnostic/educational до отдельной оценки требований.

## 8. Тестовая стратегия

- **Domain unit tests:** TS формулы, единицы, границы, округления, provenance/freshness.
- **Differential tests:** один и тот же JSON input проходит legacy Python и web TS; сравнение по type-specific tolerance.
- **DICOM tests:** public/synthetic/approved de-identified files, multi-frame, codec variants, malformed metadata, missing PixelSpacing.
- **Geometry tests:** image-to-screen mapping, transforms, rotation, resize, HiDPI, freehand serialization.
- **Application tests:** study lifecycle, cancellation, local persistence, revision conflicts, expiry/clear.
- **Browser E2E:** open study, select frame, cine, manual measurement, calculate, save/reload, export report.
- **Performance tests:** cold start, first decoded frame, frame switching/cine fps, memory high-water mark, cache eviction.
- **Security/privacy tests:** no DICOM in network on local flow, no PHI in logs/URLs, XSS-safe metadata and dependency audit.

Все web golden fixtures должны иметь соответствие с локальными источниками `gold/` и соответствующими тестами исходного проекта; не переносить PHI-содержащие файлы из `gold/` без проверки и явного разрешения. При необходимости создавать synthetic replacements.

## 9. Лицензирование и связь с SonoForge

- Исходный SonoForge лицензирован GPL-3.0. Перенос/адаптация доменного кода, тестов, UI-активов или документации в отдельный репозиторий требует сохранить уведомления, соблюсти GPL-3.0 и включить необходимые third-party notices.
- TypeScript-перенос формул — отдельная реализация, но если он является адаптацией существующего кода/тестов, вопрос производной работы нужно решить до выбора другой лицензии; не считать новый язык автоматическим обходом GPL.
- Не копировать сторонние иконки/шрифты/код без проверки их лицензии.
- Поддерживать версию источника, на которой основаны golden vectors; изменения формулы сопровождаются changelog и пересчётом/утверждением expected results.
- Автоматически синхронизировать весь Python `domain/` как submodule не рекомендуется: это добавляет runtime/build coupling и не даёт чистого TS-контракта. Если выбирается Pyodide, зафиксировать это в ADR и отдельном lockfile/профиле.

## 10. Риски и решения

| Риск | Последствие | Снижение риска |
|---|---|---|
| Не все echo transfer syntaxes доступны в браузерном decoder | Файлы нельзя открыть локально | Этап 0 проверяет representative files; strategy: codec WASM либо DICOMweb rendered-frame fallback, без потери измерительной точности |
| TS-перенос формул расходится с desktop | Неверные результаты/дрейф реализации | Python oracle + golden tests, release checklist и ревью по формуле/единицам |
| Pyodide слишком тяжёлый | Медленный старт/сложный bundle | Только сравнительный spike; не делать обязательным без измерений; lazy-load рантайма |
| Большой cine превышает browser memory | Tab crash/потеря сессии | Worker, bounded LRU, OPFS при поддержке, потоковое чтение кадров, graceful memory warning |
| DICOM содержит PHI | Утечка данных | Local-first, сетевой аудит, sanitized errors, opt-in PACS, CSP и тесты отсутствия исходящего трафика |
| Браузер/PACS блокирует cross-origin access | DICOMweb не работает | Явные CORS требования и deployment guide; не обходить browser CORS |
| Дублирование domain между проектами | Дрейф формул | Веб-каталог паритета, общие golden vectors, governance изменения формул |
| Клиническая трактовка educational tool | Риск неправильного применения | Явные ограничения назначения, не выдавать «диагноз», отдельная клиническая валидация до смены позиционирования |

## 11. Критерии MVP

MVP считается готовым для внутреннего/исследовательского пилота, когда:

1. Отдельный web-репозиторий собирается и запускается независимо от SonoForge Desktop.
2. Локальные test DICOM можно открыть и просматривать в поддержанном browser/codec matrix.
3. Есть cine, базовое управление изображением и корректный metadata display.
4. Ручные измерения и freehand/landmarks привязываются к исходному изображению и сохраняются.
5. Перенесённые формулы и калькуляторы перечислены; каждый включённый расчёт совпадает с Python golden vectors в определённом допуске.
6. Авто-сегментации, ONNX runtime и модели не загружаются и не выполняются.
7. Локальный сценарий не отправляет файлы или PHI по сети; это подтверждено тестом.
8. Есть session save/restore, export report, инструкции и ограничения браузеров.
9. Документированы известные ограничения, поддержанные transfer syntaxes, precision/performance baseline и non-diagnostic status.

## 12. Оценка и планирование

В `docs/web_build_feasibility.md` исходного репозитория ранее оценены ориентиры: Tier 0 viewer — **12–16 человеко-недель**, Tier 1 web client — **28–40**, полный паритет — **60–90**. Эти оценки были сделаны для более общего web scope и не являются оценкой именно этой спецификации.

Для данной спецификации не надо механически вычитать «2–3 недели AI»: DICOM decode, UI, Doppler/M-mode, калькуляторы, ручные инструменты, отчёты и регрессионные тесты останутся значительными затратами. После этапа 0 нужно пересчитать отдельно:

- **MVP просмотра + базовые ручные измерения + несколько критичных калькуляторов**;
- **расширенный релиз со всеми включёнными калькуляторами, Doppler/M-mode/ECG и PACS**.

Репозиторий для spike создаётся заранее; production-код и обещания по срокам — только после прохождения спайка и подтверждения codec matrix.
